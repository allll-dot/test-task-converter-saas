# Call Statistics

Прототип SaaS-сервиса, который принимает MP3-записи звонков и превращает их в
структурированную аналитику. AI-контур работает локально и не требует платных
API: `faster-whisper` транскрибирует аудио, а Ollama формирует проверяемый JSON.

## Запуск

```bash
docker compose up --build
```

При первом запуске сервис `ollama-init` автоматически загрузит бесплатные
локальные модели `qwen3:8b` и `nomic-embed-text`. Поэтому первый запуск займёт
заметно больше времени и потребует несколько гигабайт свободного места.

Swagger будет доступен по адресу `http://localhost:8000/docs`.

Перед запуском API сервис `migrate` выполняет `alembic upgrade head`. Схема БД
управляется миграциями и не создаётся приложением во время старта.

Для загрузки используется демонстрационный заголовок `X-Organization-ID`.
Это граница tenant в прототипе, а не замена production-аутентификации.
Сервис `seed` идемпотентно создаёт организацию
`00000000-0000-0000-0000-000000000001`. Этот UUID можно сразу использовать в
Swagger; в dashboard он подставляется автоматически.

## Разработка

```bash
python -m venv .venv
source .venv/bin/activate
pip install -e '.[dev]'
alembic upgrade head
pytest
```

Для запуска локальной транскрибации:

```bash
pip install -e '.[local-ai]'
```

Модель Whisper по умолчанию — `small` на CPU с `int8`. Для структурированного
анализа ожидается Ollama с моделью `qwen3:8b`. Названия моделей и адрес Ollama
настраиваются через переменные окружения.

`faster-whisper` не определяет роли участников. До подключения диаризации или
разделения стереоканалов спикер сохраняется как `unknown`, а
`manager_talk_ratio` возвращается как `null`, а не вычисляется из догадки.

После сохранения MP3 API ставит задачу `calls.process` в Redis. Celery-воркер
независимо выполняет транскрибацию, расчёт метрик и структурированный анализ.
Количество воркеров можно увеличивать независимо от API.

Агрегированная статистика доступна через `GET /api/v1/statistics`. Все запросы
считают данные только для организации из заголовка `X-Organization-ID`.

Dashboard доступен по адресу `http://localhost:8000/dashboard`. Для загрузки
данных укажите UUID демонстрационной организации. MP3 можно загрузить прямо на
первом экране. Экран показывает общее число звонков, конверсию в запись, среднюю
оценку качества, длительность, распределения исходов и последние обработанные
звонки. После загрузки dashboard опрашивает статус и обновляется по завершении
анализа. Данные для таблицы предоставляет tenant-изолированный
`GET /api/v1/dashboard/calls`.

Анализ также определяет исход записи на приём: запись создана, не создана,
перенесена, отменена, неприменима или неизвестна. Дата, время и услуга
сохраняются только при наличии в транскрипте. Dashboard будет показывать
конверсию в запись, распределение исходов, качество звонков и динамику по
периодам; RAG-чат останется дополнительным способом исследовать причины.

## RAG по транскриптам

После основного анализа воркер разбивает транскрипт на фрагменты с таймкодами,
получает бесплатные локальные embeddings через `nomic-embed-text` в Ollama и
сохраняет их в PostgreSQL с расширением `pgvector`. Сбой индексации не отменяет
готовый анализ звонка: dashboard и API результатов продолжают работать.

Задать вопрос по всем звонкам организации или по одному `call_id`:

```http
POST /api/v1/analytics/ask
X-Organization-ID: 00000000-0000-0000-0000-000000000000
Content-Type: application/json

{
  "question": "Какие возражения по стоимости встречались?",
  "call_id": null
}
```

Ответ содержит `sources` с идентификатором звонка, текстом и начальным и
конечным таймкодами. Векторный поиск всегда ограничен `organization_id`.

## Ограничения прототипа

- роли участников без диаризации остаются `unknown`;
- факт реального визита после записи требует интеграции с CRM;
- `X-Organization-ID` демонстрирует tenant boundary, но не является авторизацией;
- модели рассчитаны на демонстрационный локальный запуск, а не на SLA production.

## Нагрузка 16 000 звонков в месяц

API не ждёт транскрибацию: оно сохраняет файл, создаёт запись со статусом
`pending` и отправляет идентификатор в Redis. Celery-воркеры не хранят локальное
состояние и масштабируются независимо от API.

Количество воркеров нельзя корректно вывести только из числа звонков. Расчёт
должен учитывать суммарные аудиоминуты, пиковую скорость поступления и real-time
factor транскрибации на выбранном CPU/GPU:

```text
worker_hours = audio_hours × real_time_factor
workers = ceil(worker_hours_in_peak_window / available_peak_hours)
```

Например, при средней длительности пять минут объём составит 80 000
аудиоминут в месяц. Итоговое число воркеров определяется нагрузочным замером на
целевом сервере, после чего добавляется запас на пики и повторные попытки.

«Бесплатно» в прототипе означает отсутствие платы за внешние AI API. Серверные
CPU/GPU, дисковое пространство и эксплуатация при production-нагрузке всё равно
имеют стоимость.

## Что изменить для production

- хранить аудио в S3-совместимом object storage, а не на общем volume;
- заменить демонстрационный заголовок полноценной аутентификацией и проверкой
  членства пользователя в организации;
- добавить idempotency key загрузки и отдельную dead-letter queue;
- ограничить квоты по аудиоминутам и параллелизм по организации;
- добавить метрики времени очереди, длительности этапов, ошибок и стоимости;
- задать сроки хранения аудио и процедуру удаления персональных данных;
- синхронизировать факт состоявшегося визита с CRM или системой расписания;
- масштабировать transcription, analysis и embeddings как отдельные очереди.

Вызов считается успешно проанализированным только после сохранения транскрипта,
метрик и валидированного структурированного результата. Ошибка дополнительной
RAG-индексации не меняет статус готового основного анализа.
